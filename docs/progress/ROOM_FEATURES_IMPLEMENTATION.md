## Objective

Remove volatile Death Defiance offer-state authorship, then add the four
remaining room-feature families that materially affect modeled run state:

1. selected successful Natural Resource interactions;
2. fixed Postboss Pools of Purging;
3. Shrines of Hermes with purchase, rush, and delayed delivery; and
4. Stygian Wells with complete inventory and consequential item effects.

The editor presents each feature only in its owning physical room. Each
feature uses the room's one Overview and one ranked Room Timeline. Resources,
Shrines, and Wells also receive read-only route indexes that navigate to their
authoritative room feature; Pools remain fixed and need no index.

The runtime-offer correction lands first so every current and future trait or
item source consumes one stable fallback contract rather than adding another
Death Defiance input. After that correction and before the four room features,
replace the current derived-completion room exception with occurrence-backed
automatic completion rooms. The completion correction is required by the
feature scope itself:

- Pool, forced Shrine, and forced Well need Postboss-local state and actions;
- delayed Shrine delivery can mature in a Boss and needs an ordinary required
  pickup host with exact acquisition ordering; and
- keeping either physical room derived would preserve a second state, action,
  acquisition, finding, focus, and UI path for later gates to extend.

The intended completion tail is:

```text
selected Preboss occurrence --fixed exit--> automatic Boss occurrence
  --fixed exit--> automatic Postboss occurrence when declared by the layout
  --fixed exit--> next biome Intro occurrence or the configured route boundary
```

Completion remains a catalog/layout sequencing concept and a useful editor
outline. It stops being a distinct room-state or semantic-address kind. Boss
and Postboss own the same occurrence lifecycle, features, action timeline,
acquisition sites, and exits as other physical rooms; only their presence and
outgoing targets are declaration-fixed rather than user-selectable.

## Locked Cross-Cutting Decisions

### 1. Runtime offer volatility is declaration-contained

The authored project records the preferred trait or item outcome and simulation
assumes that outcome succeeds. It does not persist a general
`deathDefianceConditionMet` value on trait offers, Shops, Nemesis results,
Jeweled Pom results, future Shrine/Well offers, or nested item results.

The catalog retains each source requirement and the exact bounded fallback data
from the runtime-offer audit. The five volatile trait declarations each own
three ordered, distinct, requirement-free alternatives from the same giver.
Evaluation removes the other two authored screen members and anything already
unavailable in the simulated prefix, then publishes exactly one resolved
fallback beside the selected result. Jeweled Pom uses the same Hades rule
without inventing a separate keepsake mechanism.

Item fallback edges belong to an exact pool membership. World Shop, Shrine,
Well, Twist, and Nemesis do not share a global Last Stand replacement. Each
selected item action likewise publishes at most one exact fallback. Production
semantics are only `try X; if X is unavailable, try Y`; there is no recursive
walk or encoded Last Stand/Travel Deal branch. A fallback item's own edge may
serve a separate later action.

The current application does not yet serialize the future game execution-plan
protocol. This gate establishes an explicit engine-owned resolved-fallback
product on the evaluated/materialized selected result so that the later
execution-plan compiler emits one fallback identity, never the declaration's
three-candidate trait list or an authored condition. Do not add a premature
game-module adapter or place derived fallback data in the persisted project.

Gorgon Amulet retains one narrowly scoped authored phase trigger because that
fact controls whether Athena appears and whether the pending keepsake use
advances. Rename or narrow its contract so it cannot be reused as a generic
offer condition. Once Athena appears, her selected trait uses the ordinary
runtime fallback product.

### 2. Boss and Postboss are automatic occurrences

`AuthoredBiomePlan` owns a declaration-shaped `completionOccurrences` product:
one Boss `RoomOccurrence` and the layout's optional Postboss
`RoomOccurrence`. Each has a stable occurrence ID, declaration-fixed game
name, complete occurrence state, acquisition sites, encounter state, feature
payloads, and one `roomActions.order`.

These occurrences are not stored in `BiomeTopology.occurrences`. Topology
commands cannot add, remove, replace, or select them. A shared biome occurrence
locator/mutator admits both topology occurrences and automatic completion
occurrences for genuine occurrence-local commands; topology mutation remains
limited to topology owners.

The catalog owns the mandatory completion order. Simulation appends the Boss
after the selected Preboss and then appends the declared Postboss before the
transition effects.

Boss and Postboss occurrence state always persists. Both rooms are reached when
their selected Preboss is reached, including in the configured final biome.
Postboss Room Features and their actions therefore remain active at the route
tail. Its declaration-fixed exit targets the next biome Intro when one is
configured and otherwise ends at the modeled route boundary. Route extension
or shrinking changes only that target; it neither activates/deactivates nor
deletes Postboss-local state.

### 3. Completion-specific room state and addresses are retired

The automatic occurrences absorb the current completion-owned authored state:

- Boss Judgment targets move under the Boss occurrence's exact
  `bossDefeated` outcome owner;
- Boss Steady Growth uses the ordinary phase-local sparse target already used
  by authored encounters;
- Postboss action order, Keepsake Rack disposition, and immediate equip results
  move under the Postboss occurrence; and
- `echoKeepsakeReplayResults` stays biome-owned because it belongs to the next
  biome-start replay rather than either physical completion room.

`CompletionRoomAddress`, `CompletionRoomActionAddress`, and
`CanonicalCompletionRoom` are deleted once no semantic owner requires them.
Boss-specific lifecycle events such as `bossDefeated` remain explicit events
owned by the Boss occurrence and phase. Transition counter resets remain on
the catalog completion sequence, not on either occurrence.

The catalog layout's protected automatic membership and fixed edge targets are
the only completion-specific authority that remains. There is no separate
completion room materializer, action roster, lifecycle timeline, exit settler,
finding address, focus route, or final-Postboss successor gate.

### 4. Room declarations own concrete feature facts

The Hades II catalog declares which exact rooms can or must contain each
feature, along with feature-specific static facts such as supported resource
families, inventory profile, and forced versus optional placement. Normalize a
closed room-feature vocabulary one concrete feature at a time.

This is not an effect DSL or universal object registry. Feature behavior,
commands, candidate policy, and simulation stay in their owning engine
modules. Do not infer feature support from biome letters, room labels, room
kind, or React branches when exact room declarations can own it.

### 5. One room chronology with feature-owned actions

Pool sales, Shrine purchases, and Well purchases are closed
`RoomActionReference` variants in the host occurrence's single
`roomActions.order`. Their Overview controls own participation; the shared
timeline owns rank and movement. No feature receives a purchased/sold set or a
private order.

Extend the current Shop-only Overview-membership row binding into one narrow
bound descriptor usable by all Overview-owned action memberships. This is an
application presentation cleanup, not a generic Store domain model.

The action meanings remain distinct:

- Pool sale removes a trait;
- Shrine purchase schedules or rushes a later required pickup; and
- Well purchase applies one atomic paid effect.

World Shop processing must not be generalized wholesale. Reuse only the
three-slot generation, same-slot refill, action-order, and acquisition helpers
whose contracts genuinely fit.

### 6. Inventory slots and generations have stable identities

Pool, Shrine, and Well inventories use declaration-keyed physical slot
identities. A Travel Deal refill is a later generation in the same physical
slot, not a simultaneous fourth slot. Action references address the stable
offer generation rather than its current item identity.

Editing an offer payload does not change participation or rank. Removing a
feature or invalidating its source retains structurally representable stale
payload/action state with an exact repair path.

Every offer generation retains its preferred item identity even when the item
has a volatile live requirement. The evaluated result carries the exact
pool-local fallback established by Gate A. Context-invalid slot membership
remains visible for ordinary catalog or history reasons, but missing-Last-Stand
volatility never creates an authored condition, picker, or repair loop.

Travel Deal still excludes the item actually purchased when it regenerates the
physical position. The general fallback edges make both possible live branches
safe: Last Stand can fall back to Armor, and a separately requested Armor
refill can use Armor's own pool-local fallback if the purchase actually became
Armor. The engine and game module do not encode why either edge exists.

### 7. Purchase and pickup remain different lifecycles

A World Shop or Well purchase is atomic and does not invoke Time Piece,
Artificer, Sea Star, Echo last-reward recording, or another pickup-only
interaction.

A Shrine purchase does not acquire its item. Rush and maturity create a real
required pickup that uses existing reward, trait, Pom, acquisition-role,
alternative-interaction, finding, and settlement machinery. Purchase plus rush
is one ranked source action: that action executes purchase, rush, and mandatory
same-room pickup settlement, and it owns the pickup-resolution controls. It
does not create a second ranked Rush or pickup row. Only a delayed delivery
that materializes in a later host becomes a separately ranked required
acquisition in that host.

Automatic Boss occurrences are ordinary delivery hosts. A delivery maturing
after Boss End encounter can share the Boss occurrence's pre-outgoing
acquisition ordering without a completion-specific settlement path.

### 8. Scheduled delivery separates source and host ownership

Each participating non-rushed Shrine offer derives one runtime pending delivery
keyed by its stable source offer generation. The authored source retains only
the item, delay, and rushed disposition; no independent pending flag or pending
object is persisted. Evaluation derives the reached delivery host from the
encounter-event walk.

Materialization creates a concrete required acquisition entry at that host.
The host entry owns acquisition-time trait, Pom, and alternative-interaction
detail. If an upstream route or delay edit changes the derived host, the old
host entry remains stale and repairable while the new host begins unresolved.
The engine never copies or implicitly reparents the old pickup detail. If the
old host is structurally deleted, ordinary topology-impact handling owns its
removal.

The host occurrence owns pickup participation and chronology. Extend the
existing acquisition-settlement seam for this source/host split rather than
copying an acquisition tree into the pending trait or adding a Shrine-private
timeline.

### 9. Route indexes are navigation, not authoring

Resources, Shrines, and Wells receive separate transient route panels. Their
projections consume engine-authored placement/instance products plus exact
workspace destinations. They do not reconstruct spacing, feature eligibility,
inventory, or findings.

- Resources show four family rows, each unplaced or linked to its selected
  room.
- Shrines and Wells list every authored instance, including forced Postboss
  anchors at the configured route boundary, with a compact inventory/purchase
  summary.
- Clicking a placed row navigates to the exact Room Feature in the owning
  occurrence workbench.
- Add, remove, inventory, purchase, rush, duration, Twist, and sale controls
  remain room-local.

Purging Pools have only three fixed route locations and receive no route panel.

### 10. Retained-invalid authoring remains visible

Commands enforce structural shape and known catalog identities. Evaluation
owns contextual legality. A later route, room, inventory, loadout, or trait
history edit may make a placement or action unavailable without deleting it.
The editor retains the exact value, finding, and repair interaction.

The implementation must not hide a structurally supported feature because its
current candidate domain is empty, silently move a resource success, reroll an
inventory, clear a delivery child when its host changes, or normalize a stale
purchase/sale out of the timeline.

### 11. Strict schema boundaries

The locked base project schema is 53. Each gate that adds or relocates
persisted state advances the strict schema exactly once:

- Gate A: schema 54 — remove general Death Defiance authored conditions and
  retain only Gorgon's phase trigger;
- Gate B: schema 55 — automatic completion occurrences;
- Gate C: schema 56 — selected Resource successes;
- Gate D: schema 57 — Purging Pool inventory and sales;
- Gate E: schema 58 — Shrine inventory, purchases, and delivery state; and
- Gate F: schema 59 — Well inventory, purchases, and consequential children.

The production decoder accepts only its current schema. Each transition gets
an explicit migration CLI step and named migration tests. There is no dual
field, compatibility decoder, runtime repair, or schema bump for presentation
alone.

Gate A removes the obsolete condition fields from every checkpoint. Gate B
then necessarily rewrites the checkpoint corpus because both completion-room
semantic addresses change. Perform both rewrites before feature fixtures are
added.

## Delivery and Review Routine

Each implementation gate begins from the clean commit produced by the prior
gate and lands as one coherent Conventional Commit.

1. The main session records the gate's base commit, exact scope, exclusions,
   authorities, and narrow acceptance tests.
2. A fresh executor owns the complete vertical slice and runs only narrow
   owning-lane tests while implementing.
3. A fresh sibling reviewer remains read-only and reviews the exact gate diff
   against this locked plan, named audits, durable authorities, and validation
   results.
4. Accepted findings return to the executor or one narrowly owned remediation
   worker. One bounded verification pass follows material corrections.
5. The main session performs the final holistic diff review and commits only
   after confirming deletion of the superseded path and absence of unrelated
   work.

Do not run `npm run check` after each gate. Use the narrowest truthful catalog,
engine, planner, UI, contract, product, migration, and changed-test lanes for
the changed ownership. Reserve the complete gate for Gate G.
