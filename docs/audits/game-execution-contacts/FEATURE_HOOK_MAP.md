# Planner feature → native hook map

This is the current implementation map from published planner facts to native
Hades II contacts. Start here when revisiting an executor feature. One row is
one coherent intervention; multiple hooks in a row are deliberately not
flattened into independent features. Repeated native function names have
different scoped owners.

[Game Integration Boundary](../../design/GAME_INTEGRATION_BOUNDARY.md) owns
policy. This map records its concrete application; the [family inventories](README.md)
retain detailed source evidence and bounded uncertainties. The engine's
`packages/planner-engine/src/execution-plan/model.ts` owns the published union.
Executor owners below are relative to `src/mods/` in the Run Planner game module
repository, not modules in the planner. Native symbols refer to the inspected
Hades II scripts; registration alone is not evidence of a native function.

Approaches:

- **Insert** — supply the published answer or a native forcing operand.
- **Select** — steer the specific native random decision or candidate.
- **Bind** — carry exact owner/context between necessary contacts.
- **Check** — use the existing admission, DAG or room checkpoint.
- **Native** — leave the effect to the game; a simulated fact is not itself
  an instruction to add an actuator.

Native application remains native in every row. “Insert” does not mean
recreating a purchase, encounter, trait application or clock. Context across
callbacks is justified only for the consumer and retirement boundary stated
below. Source-backed and harness-tested contacts are not blanket claims of
complete-route live verification.

## Acquisitions, trait screens and levels

Source families: `InteractLogic.lua`, `UpgradeChoiceLogic.lua`, `TraitLogic.lua`,
`StoreLogic.lua`, `RoomLogic.lua`. Details:
[traits and offers](TRAITS_AND_OFFERS.md). Acquisition completion releases
steering dependencies; it is not proof of the player's retained result.

A shared source is not a unique acquisition owner. A trial publishes separate
chosen/spurned acquisitions under one incoming reward. The source and producer
indexes retain both; the native loot identity selects the published owner at
materialization. Capture producer context before spawning, but resolve the
transaction only once the object identity exists. This does not add a timing
check or select an owner by readiness.

## Maintenance and evidence

Update the affected row when a feature changes: published input, executor
owner, actual native contacts, approach, lifetime and retained native work.
Remove retired contacts rather than appending historical alternatives. If a
new hook has no row, identify which planner feature or necessary coordination
boundary it serves before accepting it. UI registration, file transport and
module bootstrap are not gameplay interventions; their owners are `host/`,
`runtime/composition.lua` and `src/main.lua`.

This map does not turn diagnostics into assertions. Existing admission,
exact-owner DAG readiness and room conformance remain the only authorities
for their checks. Acquisitions can complete steering before the player's final
state is checked. Full diagnostic frames must never become state-repair input.

Live gaps remain explicit in the family inventories: Fields placement,
Spell/Path presentation, nested consequences, later-biome contacts, and
differing-source reward preparation with keepsake/Devotion provenance. Native
source and coroutine witnesses explain why contacts are retained; they do not
prove every host/mod interleaving. Reopen the affected row with a concrete
trace rather than rebuilding the entire map or adding speculative safeguards.
